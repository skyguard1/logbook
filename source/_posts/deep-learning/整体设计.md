<div>1、背景<br/><p>在 DAU已超过6亿，其业务产品包含新闻，视频，微视，QQ，浏览器，看点等十多种，因此一个优秀的推荐系统尤为重要。作为推荐系统的原材料“特征”是重中之重，高效的生产加工用户各种特征是推荐系统卓越的关键，作为的中台产品致力于高效的实现用户行为接入，序列加工，统计特征生产，关系特征计算等，并以统一高性能的在线服务对外提供服务。</p>
<h1>2、名词解释</h1>
<ul><li>
<p>兴趣标签：类别/类目/标签/明星等各种属性都可以统称为兴趣标签</p>
</li>
<li>
<p>兴趣点特征：兴趣标签+权重（若干）的集合，这里包含2种计算方式</p>
<ul><li>
<p>统计方式：基于用户行为流水结合item sideinfo通过统计方法来计算兴趣点</p>
</li>
<li>
<p>模型方式：通过模型的方式挖掘兴趣点</p>
</li>
</ul></li>
<li>
<p>显式兴趣：用显式兴趣标签来描述的用户兴趣</p>
</li>
<li>
<p>隐式兴趣：用embedding描述的用户兴趣</p>
</li>
</ul><h1>3、设计目标</h1>
<ul><li>
<p>支持业务流水的统一接入，包含前端上报和后端上报，治理流水和非治理流水</p>
</li>
<li>
<p>支持配置化，插件化的序列，用户特征，物品特征，用户物品交叉等特征的加工能力</p>
</li>
<li>
<p>支持分钟级别和月级别固定窗口、滑动窗口统计特征，持续累积统计特征的计算</p>
</li>
<li>
<p>统一画像服务出口，包含人口属性（年龄，性别，学历等），实时序列，基于窗口的统计特征（物品特征，用户用户特征，用户+物品交叉特征）</p>
</li>
</ul><p>TRS统一测试数据跑通流程[内部链接已移除]</p>

<p>整个建模方法是采用分层递进建模，下面对每一层建模做简单说明：</p>
<p>1）、序列与统计属性建模：</p>
<p>i）、人口属性：离线挖掘，目标提升覆盖度和准确度</p>
<p>ii）、行为序列：用户事实行为，支持固定时间和长度，自定义的过滤与融合</p>
<p>iii）、行为统计属性：用户行为统计信息，支持自定义统计策略</p>

<p>i）、兴趣标签：根据统计特征，结合兴趣计算策略输出正，负向的用户兴趣标签</p>
<p>ii）、行为关系：基于用户行为实时构建U，I，Q之间的显示关系，通过图学习挖掘用户潜在的关系</p>
<p>3）、用户画像建模：</p>
<p>用户画像分时域，空间，情景和业务垂类画像，同时每种标签有独立版本和置信度在线计算时进行融合，有算法版本确立画像输出版本</p>

<h2>5.1、行为序列详细设计</h2>
<p>行为序列实时计算架构设计如下图：</p>
<p><img alt="" loading="lazy" src="/logbook/images/deep-learning/afbc0b74519eb9356350.png"/></p>
<p><br/></p>
<p><br/></p>
<p><br/></p>
<p><br/></p>
<p><br/></p>
<p>主要包括三部分：数据接入、数据处理、数据输出，每一部分的算子都实现了可配置化,配置的变更会5s被感知到</p>
<h3>5.1.1 数据接入（importer）</h3>
<ol><li>
<p>数据流水接入</p>
</li>
</ol><p>当前的行为实时日志支持CDMQ，包含治理流水和非治理流水。数据流水接入包括数据引入（Import算子）、数据ETL处理（Extract算子）、数据过滤（FIlter算子）</p>
<ol><li>
<p>Import算子</p>
</li>
</ol><p>读取数据源算子，用来读取数据源，比如CDMQ、HDFS。如果没有指定Import算子，则采用默认Import算子，默认读取CDMQ，而对于自定义的datasource需要实现sourcefunction接口，通过配置的方式实现。原则上importer算子无需自行实现，特殊情况也支持自行实现importer接口，再通过配置方式实现</p>
<p>Import算子配置：</p>
<p><br/></p>
<pre></pre>
<div>
<pre>{
  "importer": {
    "name": "",
    "source": {     
      "cdmq": [{
        "broker": "",
        "topic": "",
        "groupId": "",
        "offset": "latest/checkpoint"       
      }]
    }
}</pre>
</div>
<pre></pre>
<p>如果自定义Import算子，source部分不需要配置</p>
<ol><li>
<p>Extract算子</p>
</li>
</ol><p>ETL算子，用来对读取的数据做基础的ETL操作，对于非治理流水需要自行实现萃取逻辑，对于治理流水通过配置的方式实现数据处理转换</p>
<p>extrator算子配置：</p>
<pre></pre>
<div>
<pre>{
    "extractor": {     
      "name": "", // 萃取算子名字  default/自定义算子
      "key": "",// 存储唯一标示
      "custom_property": [
        {
          "property_path":"", // 自定义属性的原始路径，支持条件表达式
          "map_key": "", // 固定值，custom map对应的key
          "value": "" // 支持条件表达式
        }
      ],
      "common_property": {
        "item_id_path":"item_id", // 业务间通用的itemid，比如企鹅号，支持条件表达式
        "private_item_id_path":"vid", // 业务方的itemid，在拿不到企鹅号时，可以使用该id，支持条件表达式
        "cid_path":"cid", // 看点需要的内容唯一标示，支持条件表达式
        "item_type_path":"item_type", // item类型，可考虑换成int，需评估enum和int类型的空间的占用情况，支持条件表达式
        "event_time_path":"event_time", // 事件时间，支持条件表达式
        "report_time_path": "report_time" // 上报时间，支持条件表达式
      }
    }
  }
}</pre>
</div>
<pre></pre>
<p> </p>
<pre></pre>
<p>如果自定义Import算子，只需要指定name和key</p>
<ol><li>
<p>Filter算子</p>
</li>
</ol><p>支持不同类型的过滤，包括条件过滤、白名单过滤、黑名单过滤、通过外部接口过滤。</p>
<ol><li>
<p>条件过滤：支持条件表达式的定义，比如fun1(cid)，表示对cid进行过滤判断</p>
</li>
<li>
<p>通过外部接口过滤：调用外部接口来进行过滤判断，默认支持的接口是http post josn方式，参数可以配置 但返回必须为true或false</p>
</li>
</ol><p>filter算子配置：</p>
<pre></pre>
<div>
<pre>{
    "filter": {
      "condition": "fun1（cid）",  //支持条件表达式 
      "whitelist": "",     
      "blacklist": "",  
      "api": ["p1","p2"]  //p1、p2表示接口配置
    }
}</pre>
</div>
<pre></pre>
<p> </p>
<pre></pre>
<p>目前支持条件过滤。其他类型的过滤二期支持</p>
<h3>5.1.2、数据处理（processor）</h3>
<p>该部分将数据处理成不同存储需要的数据结构，其中完成对维表关联、id转换等</p>
<ol><li>
<p>Process算子</p>
</li>
</ol><p>处理算子，包含一系列Processor算子，已内置id转换Processor、维表关联Processor等，也可以自定义Processor算子</p>
<p>processor算子配置：</p>
<pre></pre>
<div>
<pre>"processor": [     //数组元素的位置代表处理顺序
    {
      "name":"",
      "aggr": {
        "window": {
          "size": 1,
          "slide": 2
        },
        "aggr_key": "user_id", // 支持条件表达式
        "feature_name": "test1", // 支持条件表达式
        "feature_value": "1" // 支持条件表达式
      }
}]</pre>
</div>
<pre></pre>
<p> 自定义Processor算子步骤：</p>
<ol><li>
<p>继承Processor类，增加Process注解，重写process方法，编写处理逻辑</p>
</li>
<li>
<p>在配置中增加该算子，并设置处理顺序</p>
</li>
<li>
<p>如果涉及到访问外部接口，尽量采取异步io的方式调用，同时根据实际调用情况对接口支持的QPS调优，避免出现反压，以及影响到checkpoint</p>
</li>
</ol><ol><li>
<p>维表关联与转换</p>
</li>
</ol><p>对于维表的访问采取异步的方式，视调用压力来决定是否增加缓存层以及缓存层的实现复杂程度。</p>

<h3>5.1.3、实时滑动窗口统计（processor）</h3>
<p>为了满足对于长时间序列的统计，比如统计统计看点的某item在最近1小时的点击次数，具体设计如下：</p>
<p>1、实时滚动统计</p>
<p>a、基于滚动时间窗口计算用户/item的统计量，窗口支持动态滑动（例如5分钟，一小时，一天等），统计更新频率：毫秒</p>
<p>b、对于一条消息，会同时落到不同大小的窗口中，比如0：04的消息会落到0：00~0：05的分钟级窗口、0：00~1：00的小时级窗口、20211122的天级窗口</p>
<p>2、在线滑动计算</p>
<p>a、根据统计的时间段，汇总不同大小的窗口，可以是同一大小的窗口汇总，比如多个分钟级窗口；也可以是不同大小的窗口汇总，比如分钟级和小时级窗口</p>
<p>b、查询时会多查询一个窗口，保证统计时间段的完整性，同时也会产生可接受的误差</p>
<p>淘汰机制：写入时根据不同大小窗口的最大保留数，对旧窗口进行淘汰</p>
<h3>5.1.4、数据输出（exporter）</h3>

<h3>5.3.4、近线大窗口滑动设计</h3>
<p>大窗口滑动任务，指窗口大小超过30分钟的任务。对于该类型任务，无法通过在单个任务中开大窗口直接进行，会因为中间数据过多、计算集群不稳定等因素导致任务失败。根据用户配置的计算逻辑，落地中间数据到HDFS中，具体如下：</p>
<ol><li>
<p>首先落地5分钟中间数据；</p>
</li>
<li>
<p>如果窗口超过2小时，会落地1小时中间数据；</p>
</li>
<li>
<p>如果窗口超过1天，会落地1天中间数据；</p>
</li>
<li>
<p>如果窗口超过30天，会落地30天中间数据。</p>
</li>
</ol><p>举例来说，如果窗口大小为1天，假如2021-09-02 12:00:13触发计算任务，此时需取2021-09-01 12:00:13 ~ 2021-09-02 12:00:13，因为滑动的最小步长为5分钟，实际取2021-09-01 12:00:10 ~ 2021-09-02 12:00:10的数据，实际取</p>
<p>1）2021-09-01 13:00:00 ~ 2021-09-02 12:00:00内23个1小时的聚合数据</p>
<p>2）2021-09-01 12:00:10 ~ 2021-09-01 13:00:00内10个5分钟聚合数据</p>
<p>3）2021-09-02 12:00:00 ~ 2021-09-02 12:00:10内2个5分钟聚合数据</p>

<p>1）Import算子数据</p>

<h2>5.4、异常处理及回溯</h2>
<h3>5.4.1 容错与数据一致性（原则不丢可重）</h3>
<p>不丢：利用flink checkpoint机制来保证，异常重启可从checkpoint快照恢复。如果不开启checkpoint，异常时会从offset断点恢复，由于是自动提交offset，会发生offset提交了，但消息未正常写入存储的情况。开启checkpoint会保证在checkpoint完成时才提交offset，至少保证消息不丢。</p>
<p>可重：数据一致性语义采用至少一次。故障重启从checkpoint中保存的offset恢复，结果数据可能重复，重复数据由使用方去重。不采用精确一次语义的原因是需要用幂等写入/事务写入的方式来实现，复杂性增加，同时处理时延会上升。另外，周期性的离线修正会消除重复数据</p>
<h3>5.4.2 异常处理</h3>
<p>如果重启或异常导致数据堆积由此会引发最新的消息延迟，这里为了避免此问题，解决方案为：代码中留有判断逻辑，设置延迟的时间阈值，小于等于这个阈值的为短暂延迟，大于的为中长时间延迟。</p>
<p>短暂延迟：理解为可在短时间内自然赶上，影响很小，则继续从checkpoint存储的offset断点消费即可</p>
<p>中长时间延迟：为了不影响下游使用，不从checkpoint存储的offset位置消费，而是从最新位置消费。同时另一个程序或者一段逻辑将断点位置到最新位置的记录补写到存储中。需要持续保存处理完的消息offset</p>
<h3>5.4.3 回溯与矫正</h3>
<p>因为redis存储有一定的长度限制，同时整个实时运行过程中会发生各种异常导致数据的丢失或者重复。为了解决此问题，这里采用周期性离线的异步地修正实时数据：实时数据一直在持续写入，如果需要离线修复，采用消息队列，将并发的离线修正和实时写入的操作转换成顺序处理。并且，如果一个请求的用户没有对应的行为序列，这里才通过异步的方法从离线数据中回溯该用户的行为序列</p>
<h3>5.5、兴趣点计算设计</h3>
<p>兴趣点分为两种方式一种是通过模型的方式计算，另一种是通过规则统计的方式。对于模型的本系统不包含模型的训练和serving，本系统通过调用模型的方式将特征输入到模型中进行预测。</p>
<p>数据流设计如下：</p>

<p>基于规则的兴趣点计算算法设计（默认算法，业务可定制）：</p>
<p>用户偏好程度 = 行为类型权重值 × 次数 × 时间衰减 × TFIDF值</p>
<p>行为类型权重值：根据实际业务进行设置，如对于视频类的，点击=1，看完=2，收藏=3，分享=4等</p>
<p>次数：则是行为发生的次数</p>
<p>时间衰减：则是按一定的衰减系数，随着时间衰减，这里使用牛顿热力学公式来取衰减系数。</p>
<p>TFIDF：用来衡量标签的对一个用户的关键程度。</p>
<p>热度计算公式为：热度=1×exp(-0.1556×天数)</p>
<p>TF=行为中某标签出现的次数/用户全部标签出现的次数</p>
<p>IDF=log(用户数/（带该标签的用户数+1）)</p>
