<p></p><h2>1. 离线环节</h2><p>特征在离线的更新主要分为，批量更新（天级别、小时级别）和实时更新两种。</p><h3>批量更新：</h3><ol><li>离线脚本，去批量写数据到hive表</li><li>venus 流水线定时从 hive 表读取特征数据，并根据venus 平台上注册的特征字段过滤，只保留注册后并且仍在使用的特征</li><li>将过滤后的特征数据，构建成离线词典的形式，发送到COS平台；并通知给rimos 平台</li><li>rimos平台下载COS上的批量数据并加载到 cmod 存储引擎中，供ura 服务查询</li></ol><h3>实时更新：</h3><ol><li>数据源将离线实时数据写入到kafka中</li><li>rimos 中的kafka client 消费kafka，然后将数据写入到 rimos 平台的底层存储 faster kv 中</li><li>（可选）有些数据，比如正排。会将数据通过kafka 同步到rimos faster kv的同时，写一份冷数据到tendis ssd</li></ol><h2>2.venus平台环节</h2><p>为了让特征在在线服务中生效，算法同学需要在venus平台中注册特征。venus 平台提供api 接口来返回注册好的特征字段集合。</p><p>在线服务通过 venus openapi 返回的这些信息来决定模型使用哪些特征字段；离线任务根据这些信息来决定哪些字段是可以被build 到rimos 词典中。</p><h2>3.在线环节</h2><ol><li>rank 请求feature server，获取所有模型使用的特征字段的并集（记为feature set）<ol><li>feature server 根据 feature set 去访问URA（unified resource access）服务获取 doc id 所对应的所有特征</li></ol></li><li>rank 拿回feature 之后，依次调用下游的各个模型打分服务（无量serving）<ol><li>rank 服务请求venus openapi 得到各个模型使用的特征字段</li><li>在调用模型A的打分服务的时候，只传送模型A 需要的特征字段</li></ol></li><li>在推荐请求结束之后，接入服务会再次请求feature server来dump feature，此时会 dump 整个feature set 特征（目的是为了离线训练的时候，样本中能包含所有特征，否则训练任务还得挑选包含自己用到的那部分特征的样本）</li></ol><h2>4.架构优势</h2><ol><li>引入特征服务<ol><li>将数据存储和在线特征使用解耦，对业务逻辑屏蔽底层存储细节</li><li>结合 cache 机制，可以减少业务对存储（比如redis）的访问压力</li><li>实现一次请求中不同阶段请求得到特征的一致性（比如排序和feature dump）</li><li>在线dump feature，避免离线去生成样本。而且更好保证一致性</li></ol></li><li>使用 venus 特征平台<ol><li>对特征进行有效管理，方便算法同学了解当前生效的和未生效的特征；及时下掉无用特征等</li></ol></li><li>存储格式统一为 flatbuffer，读写速度相比pb 快</li><li>正排数据引入tendis ssd 冷存储，有利于灾备和降低成本</li></ol><h2>5.可能存在问题</h2><ol><li>flatbuffer 占用空间相对pb 大一些，需要关注资源情况</li><li>flatbuffer 对于离线debug是否友好 ?</li><li>全量 + 增量数据的获取，需要读取两个key，然后做merge（虽然是在 ura 中完成），性能和存储会有冗余。是否可以考虑 inplace 更新？</li><li>推荐场景dump feature 只有20条，而搜索返回400条，如何控制dump feature 条数?</li><li>feature server 目前是没有和venus 特征平台联动，会获取所有特征字段然后在rank 处进行过滤，可能存在字段浪费</li></ol>
