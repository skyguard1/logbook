<div></div><div><h1>引言</h1>
</div><div><p>在推荐系统中，一次用户请求，大约要经过这么几个步骤，1、召回，根据画像从千万级视频池中定向召回千级候选视频；2，经过相对轻量的模型，对这千级视频进行一次初筛截断；3、接着会经过一个复杂的网络模型进行pctr预测；4、最后根据一些策略（rerank）挑选大约10~20个最佳视频返回给用户。</p>
</div><div><p>召回作为第一步，它能召回的视频上限决定了整个推荐引擎的上限，所以算法人员会从各种“角度”去刻画一个用户，尽可能提高覆盖度，那么作为工程人员，如何在有限的人力下，设计一个高度可扩展的召回系统也至关重要。</p>
</div><div><p>召回可以抽象成 <strong>f(画像，内容) 映射</strong>关系，如果画像是用户画像，则为个性化推荐；如果是item则为相关推荐；我们将一种映射称之为一个trigger。下面将介绍我们召回系统是如何支撑近400路召回实验（各个场景，含历史上线，正在服务的所有召回实验数目）。</p>
</div><div><h1>写在前面</h1>
</div><div><p>数据、第三方服务及一些必要的说明</p>
</div><div><ul>
<li>正排存储在dcache中，每个item包含若干个字段</li>
<li>倒排存储在ranklist中，一种类似redis的kv存储，具备bloomfilter过滤及交集运算的能力</li>
<li>画像大多存储于redis等kv存储中，也有一些是上层下发的（如相关推荐场景，原视频分类等信息）</li>
<li>接下来描述的召回，暂时不包含模型如hnsw之类的ann召回（ann是通过召回系统接入的，但目前ann是作为一个独立服务存在的，故不作介绍）；</li>
<li>召回是否需要走粗排，由实验人员自行在abtest系统中配置，框架会按需将trigger分组访问粗排（支持所有trigger访问同一粗排服务，也可以不同trigger访问不同粗排服务），后续介绍中不含粗排的逻辑。</li>
</ul>
</div><div><h1>整体设计</h1>
</div><div><p><img alt="" loading="lazy" src="/logbook/images/algorithm-platform/731ecbd798ed129f6667.png"/><br/>
两层架构，</p>
</div><div><ul>
<li>分发服务聚焦场景处理逻辑，以及各种条件下的过滤逻辑；</li>
<li>算法子服务负责实现各个trigger（映射关系）。</li>
</ul>
</div><div><h1>算法子服务集群</h1>
</div><div><p>我们将400多路召回，按照逻辑进行了一个简单划分，如兴趣标签类推荐、cf类推荐、全局推荐等；这些划分是通过配置文件来实现的，代码是公用一套。</p>
</div><div><h2>方案选型</h2>
</div><div><p><img alt="" loading="lazy" src="/logbook/images/algorithm-platform/38f6dfb78259aa557698.png"/><br/>
我们将网络访问也视为一种广义的计算，f(画像，内容)的实现，可以如左图这样，一次性将一个trigger的所有逻辑全部包办，这种方式比较容易理解，但是缺点也如图所示，我们有近400路trigger，如果采用左图，那么代码会爆炸，管理会很困难。</p>
</div><div><p>考虑到计算方式是很有限的，所以我们选择忽略数据，而聚焦在“计算”上，即右图的方案，<strong>最终我们实现的是一套“计算”框架，而不是若干种召回算法，每一个计算都是算子化注册进框架，并且可以根据配置任意的插拔和复用</strong>。</p>
</div><div><p>不实现任何一路trigger的完整实现，而是编写若干个“计算”和调度逻辑；trigger交由配置文件通过组合op的形式来生成（参见下一节）。</p>
</div><div><h2>方案展示</h2>
</div><div><p>trigger=f(画像，内容)，我们将trigger处理拆成3个stage:</p>
</div><div><ul>
<li>profile画像步骤，负责userID-&gt;原始画像的“计算”，如从redis中获取画像等；</li>
<li>strategy策略步骤，负责原始画像-&gt;召回画像的“计算”，可以实现一些画像的融合和过滤逻辑，如根据时间戳过滤最近观看列表，或合并多路画像等；</li>
<li>trigger召回步骤，负责召回画像-&gt;候选视频的“计算”，如多样性召回、根据权重的累加求和等；<br/>
<img alt="" loading="lazy" src="/logbook/images/algorithm-platform/37ad706abfb45936cb32.png"/></li>
</ul>
</div><div><p>将各种“计算”剥离成op，再由DAG将op进行串并连，一路trigger只需要根据配置文件即可以生成；如果现有算子不满足相关召回实验，则开发相应的算子即可。</p>
</div><div><p>举例，某trigger（假设叫tu4_2_vid）的实现要求，将<strong>实时观看列表</strong>（假设用U27表示）和<strong>离线观看列表</strong>（假设用U29表示）按照<strong>1:1的权重融合</strong>，其中实时观看列表可能有重复item，需要预<strong>过滤U27</strong>，再使用融合的画像去召回，要求每个画像item<strong>尽可能</strong>都有候选视频被召回。</p>
</div><div><p>画像配置（U29和U27原始画像的获取）</p>
<pre>&lt;root&gt;
&lt;profile&gt;
    # common是所有profile提供一个默认参数，所有参数profile都可以重置
    &lt;common&gt;
        ... # 公共参数
    &lt;/common&gt;
    &lt;profileInfo&gt;
        name=U29,U27
        &lt;U29&gt;
            ... # 当前U29需要的各种参数
            type = ProfileRedisUserOp # 画像算子名
        &lt;/U29&gt;
        &lt;U27&gt;
            ... # 当前U27需要的各种参数
            type = ProfileRedisUserOp # 画像算子名
        &lt;/U27&gt;
    &lt;/profileInfo&gt;
&lt;/profile&gt;
&lt;/root&gt;
</pre>
</div><div><p>策略配置（U29、U27的过滤合并）</p>
<pre>&lt;root&gt;
&lt;strategy&gt;
    &lt;common&gt;
    &lt;/common&gt;
    &lt;strategyInfo&gt;
        name=U29U27StgyMerge
        &lt;U29U27StgyMerge&gt;
            pfNames = U29,U27 # 原始画像名
            type = StrategyInterest # 超级算子，基本固定该op
            # 过滤op，多个op name之间逗号分隔
            filterOpNames = U27DupOpMax1 
            # 合并op，多个op name之间逗号分隔
            calOpNames = U29U27MergeOp1 
            &lt;U27DupOpMax1&gt;
                pfNames = U27 
                # 算子op，过滤pfNames（U27）
                type = FilterDuplicateOp 
                # pfParam是上面这个op内部使用的参数，各个op自行定义，这里表示重复的item，保留分数最高的
                pfParam = calType:max
            &lt;/U27DupOpMax1&gt;
            &lt;U29U27MergeOp1&gt;
                # 注意这里用的是U27经过过滤后的画像进行merge计算
                pfNames = U29,U27DupOpMax1
                # 算子op，合并pfNames
                type = CalculateMergeOp 
                # pfName2Param为上面op内部使用的参数，各个op自行定义
                pfName2Param = U29:0.5,U27DupOpMax1:0.5
            &lt;/U29U27MergeOp1&gt;
        &lt;/U29U27StgyMerge&gt;
    &lt;/strategyInfo&gt;
&lt;/strategy&gt;
&lt;/root&gt;
</pre>
</div><div><p>召回配置（基于U29、U27融合后的画像的trigger）</p>
<pre>&lt;root&gt;
&lt;trigger&gt;
    # common仅是为所有trigger提供一个默认参数，所有参数trigger都可以重置
    &lt;common&gt;
        ... # 公共参数
    &lt;/common&gt;
    &lt;triggerInfo&gt;
        name=tu4_2_vid
        &lt;tu4_2_vid&gt;
            # 1. 配置当前trigger需要的画像
            profileKey = U29,U27 
            # 2. 配置是否需要对画像进行策略计算，也可以不配置（等效于原始画像即是召回画像）
            strategyKey = U29U27StgyMerge 
            ... # 当前召回其他参数
            # 3. 配置召回算子op，当前该算子表示多样性召回                          
            type = TriggerDivOp 
        &lt;/tu4_2_vid&gt;
    &lt;/triggerInfo&gt;
&lt;/trigger&gt;
&lt;/root&gt;
</pre>
</div><div><p>上面的配置生成的召回“tu4_2_vid”在线召回“计算”流程如下，除了最后一步输出ItemsVec外，中间所有结果都是<strong>全局可见</strong>的，即当前请求中如有其他召回，这些中间画像结果都可以使用。<br/>
如果“tu4_2_vid”召回变更需求，将多样性召回改为每个候选视频都命中尽可能多的画像，那么只需要将召回配置改为如下</p>
<pre>...
        &lt;tu4_2_vid&gt;
            ...
            # 3.2 只需要变更下面算子名即可                          
            type = TriggerAccOp 
        &lt;/tu4_2_vid&gt;
...
</pre>
</div><div><p><img alt="" loading="lazy" src="/logbook/images/algorithm-platform/eb8ca97f887ae926ca2f.png"/></p>
</div><div><h2>全自动化上线</h2>
</div><div><p><img alt="" loading="lazy" src="/logbook/images/algorithm-platform/4a1ccbed4c5065fe1bc2.png"/><br/>
上一节，我们召回已经全部由配置文件来生成（算子不满足的，新开发算子），但每上一路实验，依然需要</p>
</div><div><ul>
<li>配置profile、strategy和trigger配置文件</li>
<li>配置文件打包，同步至测试机器，测试</li>
<li>配置上传至发布平台，灰度发布</li>
</ul>
</div><div><p>这一系列环节，配置文件不能出错，要严格一致，这显然是体力活（基本不用动脑），重复的劳动就一定是可优化的，所以我们进行了配置文件托管，具体流程是</p>
</div><div><ol>
<li>实验人员通过web写入召回配置<br/>
（后台管理程序校验输入参数，合法则录入db）</li>
<li>crontab任务定时将db数据同步至七彩石<br/>
（七彩石灰度发布）</li>
<li>crontab任务定时检测七彩石数据与本地配置文件的差异，替换掉机器上有差异的配置文件<br/>
<img alt="" loading="lazy" src="/logbook/images/algorithm-platform/9b03fc28878f36f546ed.png"/></li>
</ol>
</div><div><p>至此，召回实验基本实现了全自动化上线（按运营要求，灰度发布过程需要保留）。</p>
</div><div><h2>进一步优化</h2>
</div><div><p><img alt="" loading="lazy" src="/logbook/images/algorithm-platform/c55c745cd5359e1d7648.png"/><br/>
配置已迁移至配置中心，下一步考虑将算子库剥离，算法子服务只负责框架调度，启动时由“引导程序”按需拉取不同的算子及配置，动态生成一个特定的服务。</p>
</div><div><h1>分发服务</h1>
</div><div><p>分发服务与算法自服务是一对多的关系，比如短视频个性化推荐，对应了5个算法自服务集群，个数可以根据配置文件动态调整。</p>
</div><div><h2>目标</h2>
</div><div><p>分发服务主要负责</p>
</div><div><ul>
<li>并发访问多个算法子服务</li>
<li>对候选视频进行各种过滤逻辑（黑名单过滤、播控过滤等）</li>
<li>根据场景进行不同的“计算”，如短视频底层页会进行一轮srcItem和候选视频的cos余弦相似度计算，取TopN（确保进入ranking的视频与源视频的相似度）</li>
</ul>
</div><div><h2>方案展示</h2>
</div><div><p><img alt="" loading="lazy" src="/logbook/images/algorithm-platform/23df4608c619328410f2.png"/><br/>
分发服务，逻辑上没有什么特殊的，主要是根据正排进行过滤和计算，所以正排的管理是分发服务的重中之重。</p>
</div><div><h2>正排管理</h2>
</div><div><ul>
<li>全量存储在dcache</li>
<li>本机缓存最近访问的数据（可配置，目前是缓存10min的）</li>
</ul>
</div><div><p>提到缓存，必提到的如下几个问题</p>
</div><div><h3>缓存一致性</h3>
</div><div><p>最终一致性（就单机缓存本身而言，说是顺序一致性好像也可以），目前分发服务是只读不写，而且正排字段一般不是频繁修改，故当前一致性级别已可满足。</p>
</div><div><h3>缓存击穿</h3>
</div><div><p>未考虑，原因是请求正排的视频，来自倒排，池子本身是可控的，即使有少量的视频因为延迟未更新正排，击穿缓存也在可接受范围内。</p>
</div><div><h3>防"雪崩"（防后端存储过载或失败）</h3>
</div><div><p>这个是重点考虑的，一来是踩过这个坑（因为流量突然的上涨，压垮后端存储，存储侧扩容来不及，导致线上大面积失败），另一个是dcache每次新扩字段，dcache都会重启机器，导致请求失败。所以针对后端存储失败的问题，设计了如下3级防护。</p>
